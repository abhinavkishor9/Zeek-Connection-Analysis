# Zeek Lab 02 — Connection Analysis

## Overview

This lab focuses on analyzing network connection metadata generated by Zeek from an offline packet capture. The investigation covers connection filtering, sorting, traffic summaries, HTTP correlation, and protocol-anomaly analysis.

The capture `quickstart.pcap` was reused from Lab 1 and analyzed in a separate working directory. The generated logs were examined to understand communication patterns and investigate an unusual HTTP method.

## Objectives

- Generate Zeek logs from an offline PCAP.
- Understand the structure and purpose of `conn.log`.
- Identify communicating hosts, ports, protocols, and detected services.
- Analyze connection duration, byte counts, packet counts, and connection states.
- Use `zeek-cut`, `grep`, `awk`, `sort`, and `uniq` to process connection records.
- Correlate connection records with HTTP transactions using UIDs.
- Investigate an unusual HTTP method through `http.log` and `weird.log`.
- Examine `files.log` for supporting metadata.
- Distinguish confirmed observations from potential security concerns.

## Environment

- Operating system: Ubuntu 24.04 on WSL
- Zeek version: 8.0.10
- Analysis mode: Offline PCAP
- Capture file: `quickstart.pcap`
- Working directory: `~/zeek-labs/lab02`
- Zeek executable: `/opt/zeek/bin/zeek`
- Field extraction utility: `/opt/zeek/bin/zeek-cut`

## Lab Workflow

### 1. Prepare the Working Directory

Create the directory and copy the capture from Lab 1.

    mkdir -p ~/zeek-labs/lab02
    cd ~/zeek-labs/lab02
    cp ~/zeek-labs/lab01/quickstart.pcap .

Verify the capture:

    ls -lh quickstart.pcap
    file quickstart.pcap

The capture was approximately 2.4 KB and identified as a PCAP version 2.4 Ethernet file.

### 2. Generate Zeek Logs

Run Zeek against the offline capture:

    /opt/zeek/bin/zeek -r quickstart.pcap

List the generated logs:

    ls -lh *.log

The observed logs were:

- `conn.log`
- `http.log`
- `files.log`
- `weird.log`
- `packet_filter.log`

### 3. Count Connection Records

    grep -vc '^#' conn.log

The command returned `2`, indicating two non-header records in `conn.log`.

### 4. Extract Connection Details

    /opt/zeek/bin/zeek-cut id.orig_h id.orig_p id.resp_h id.resp_p proto service duration conn_state < conn.log

The output showed two TCP connections from `192.168.1.8` to different destination IP addresses on port `80`.

### 5. Filter by Destination Port

    /opt/zeek/bin/zeek-cut id.orig_h id.resp_h id.resp_p proto service conn_state < conn.log | awk '$3 == 80'

Both connection records matched the destination-port filter.

### 6. Compare Duration and Byte Counts

    /opt/zeek/bin/zeek-cut id.orig_h id.resp_h duration orig_bytes resp_bytes < conn.log

The observed durations were approximately `0.098478` and `0.100107` seconds.

The originator byte counts were `71` and `73`, while the responder byte count was `377` for both connections.

Sort by duration:

    /opt/zeek/bin/zeek-cut ts id.orig_h id.resp_h duration orig_bytes resp_bytes < conn.log | sort -t $'\t' -k4,4nr

Sort by originator bytes:

    /opt/zeek/bin/zeek-cut ts id.orig_h id.resp_h duration orig_bytes resp_bytes < conn.log | sort -t $'\t' -k5,5nr

These commands demonstrate how connection records can be compared using measurable attributes.

### 7. Summarize Hosts and Ports

Count originator addresses:

    /opt/zeek/bin/zeek-cut id.orig_h < conn.log | sort | uniq -c | sort -nr

Count responder addresses:

    /opt/zeek/bin/zeek-cut id.resp_h < conn.log | sort | uniq -c | sort -nr

Count destination ports:

    /opt/zeek/bin/zeek-cut id.resp_p < conn.log | sort | uniq -c | sort -nr

The results showed two connections from `192.168.1.8`, one connection to each destination IP, and two connections to destination port `80`.

### 8. Correlate Connection and HTTP Records

Extract connection details:

    /opt/zeek/bin/zeek-cut uid id.orig_h id.resp_h id.resp_p service conn_state < conn.log

Extract HTTP details:

    /opt/zeek/bin/zeek-cut uid method host uri user_agent status_code status_msg < http.log

Both HTTP transactions referenced `zeek.org`, URI `/`, user agent `curl/8.7.1`, and response status `301 Moved Permanently`.

The first transaction used method `GET`. The second contained the method value `WEIRD`.

### 9. Investigate the Protocol Anomaly

    cat weird.log

The inspected record contained the event `unknown_HTTP_method`, associated with the second connection.

This confirms that Zeek recorded an unknown HTTP method. It does not independently establish malicious activity.

### 10. Review File Metadata

    cat files.log

Two HTTP-related file records reported MIME type `text/html`, with `162` bytes observed and `162` total bytes for each record.

The displayed records did not contain populated file hashes or extracted file paths.

## Key Findings

- Two TCP connection records were identified.
- Both connections originated from `192.168.1.8`.
- The destinations were `192.0.78.212:80` and `192.0.78.150:80`.
- Zeek identified the service as HTTP for both connections.
- Both connections had state `SF` and zero reported missed bytes.
- Both HTTP transactions referenced `zeek.org` and returned `301 Moved Permanently`.
- One HTTP transaction used method `GET`; the other used `WEIRD`.
- `weird.log` recorded an `unknown_HTTP_method` event for the second connection.
- `files.log` contained two HTTP-related `text/html` records.

## Assessment and Limitations

The unknown HTTP method is the primary anomaly identified in this capture. Its cause has not been established, and the available logs do not prove that the request was malicious.

The actual redirect destinations were not confirmed from the inspected fields. The HTML response contents were not independently examined.

The observed generated-log listing did not include `dns.log` or `ssl.log`. Their absence from the listing does not independently prove that DNS or TLS traffic was absent from the original environment.

Further packet-level analysis is required before drawing stronger conclusions.

## Conclusion

This lab demonstrates how Zeek connection records can be filtered, sorted, summarized, and correlated with application-layer activity.

The investigation identified an unknown HTTP method and a corresponding `unknown_HTTP_method` event. These are confirmed observations, but the available evidence does not establish malicious intent or a security incident.

This lab is intended for educational purposes and offline network-traffic analysis. Findings should be based on available evidence, with uncertainties and limitations documented explicitly.
